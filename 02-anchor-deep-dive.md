## 1. Project anatomy

An Anchor project is a Cargo workspace plus an `Anchor.toml` that tells the `anchor` CLI where programs live, which cluster to use and how to test. When you open an unfamiliar Anchor repo in an audit, these files tell you the program IDs, the Anchor version and the test setup in two minutes. \[Certain\]

### 1.1 Create one

```bash
avm install latest && avm use latest     # Anchor version manager
anchor init my_vault                     # new workspace
cd my_vault
anchor build                             # compiles + generates the IDL
anchor test                              # builds, starts a local cluster, runs tests
```

In 1.x, `anchor init` generates a **LiteSVM** test template by default (`--test-template mollusk` or `mocha` for the others), and `anchor test` uses **Surfpool** instead of `solana-test-validator` unless you pass `--validator legacy`. The CLI also implements `deploy`, `airdrop`, `balance` and `address` itself, so the `solana` binary is no longer required. \[Certain\]

### 1.2 The files

```text
my_vault/
├── Anchor.toml                  # CLI config: program IDs per cluster, wallet, test script, hooks
├── Cargo.toml                   # workspace + [profile.release] (check overflow-checks!)
├── programs/
│   └── my_vault/
│       ├── Cargo.toml           # anchor-lang / anchor-spl versions + features
│       └── src/
│           ├── lib.rs           # declare_id! + #[program] module
│           ├── instructions/    # one file per instruction (convention, not required)
│           ├── state/           # #[account] structs
│           ├── errors.rs        # #[error_code] enum
│           └── constants.rs     # seeds, limits
├── tests/                       # LiteSVM / Mollusk (Rust) or mocha (TS) tests
├── target/
│   ├── deploy/my_vault.so       # the compiled program
│   ├── deploy/my_vault-keypair.json  # keypair whose pubkey IS the program ID
│   ├── idl/my_vault.json        # the IDL
│   └── types/my_vault.ts        # TS types generated from the IDL
└── migrations/deploy.ts         # optional deploy script
```

### 1.3 Anchor.toml

```toml
[toolchain]
anchor_version = "1.x.y"         # pin it

[programs.localnet]
my_vault = "Vau1t11111111111111111111111111111111111111"

[programs.mainnet]
my_vault = "Vau1t11111111111111111111111111111111111111"

[provider]
cluster = "localnet"
wallet = "~/.config/solana/id.json"

[scripts]
test = "cargo test"

[hooks]                          # 1.x: run commands around build/test/deploy
pre_build = "echo building"
```

### 1.4 Program IDs: three places that must agree

1. `declare_id!("…")` in `lib.rs`: the ID the program checks itself against.
2. `target/deploy/<name>-keypair.json`: the key used to deploy.
3. `[programs.<cluster>]` in `Anchor.toml`: what the CLI and tests use.

`anchor keys sync` rewrites 1 and 3 to match 2. In 1.x, `anchor build` errors if 1 and 2 differ (skip with `--ignore-keys`). \[Certain\]

### 1.5 Audit quick-scan

Open these first, in this order:

| File | Look for |
| --- | --- |
| `programs/*/Cargo.toml` | `anchor-lang` version; features like `init-if-needed`, `lazy-account`, `event-cpi` |
| root `Cargo.toml` | `overflow-checks = true` in `[profile.release]` |
| `lib.rs` | Every instruction, in one list |
| `target/idl/*.json` (build it) | Every instruction's accounts with `writable`/`signer`, args, account types |
| `Anchor.toml` | Program IDs per cluster, test setup |

## 2. Life of an Anchor instruction

Every Anchor instruction runs through the same six stages, all generated by macros except stage 5. Security lives mostly in stage 4: if a check isn't generated there or written in your handler, it doesn't exist. \[Certain\]

&#91;embedded content: Life of an Anchor instruction · 6 stages\]

Stage 4 is the one to audit: it is generated from your `#[derive(Accounts)]` struct, and anything it doesn't cover (including every account in `remaining_accounts`) must be checked in the handler.

### 2.1 Stage by stage

**1. Entry.** `#[program]` generates the `entrypoint!` and a function `entry(program_id, accounts, data)`. It first checks that `program_id` equals the ID from `declare_id!` (`DeclaredProgramIdMismatch` otherwise).

**2. Dispatch.** The first 8 bytes of the instruction data are the **instruction discriminator**: by default `sha256("global:<handler_name>")[..8]`. The generated `dispatch` function matches them and calls the right wrapper. Unknown bytes fail with `InstructionFallbackNotFound`, unless you defined a `fallback` function. In 1.x you can set custom ones with `#[instruction(discriminator = …)]`. \[Certain\]

**3. Arguments.** The rest of the data is Borsh-decoded into a generated struct holding your handler's arguments, in order. Bad bytes fail with `InstructionDidNotDeserialize`.

**4. `try_accounts`.** Generated from your Accounts struct. For each field, **in declaration order**: build the wrapper type (which runs its checks: owner, discriminator, signer, program ID…), run `init` if present, then check the field's constraints. PDA bumps found along the way go into `ctx.bumps`. Accounts beyond the declared ones are not checked; they become `ctx.remaining_accounts`.

**5. Handler.** Your function runs with a `Context`. Returning `Err` aborts.

**6. Exit.** For each `mut` account wrapper, `exit()` runs: `Account<T>` re-serializes `T` into the account's data; `close = target` moves lamports and wipes the account. This is why changes to a non-`mut` `Account<T>` are lost.

### 2.2 Roughly what `#[program]` generates

```rust
// simplified from `cargo expand`
pub fn entry(program_id: &Pubkey, accounts: &[AccountInfo], data: &[u8]) -> ProgramResult {
    if *program_id != ID { return Err(ErrorCode::DeclaredProgramIdMismatch.into()) }
    let (disc, rest) = data.split_at(8);                       // (real code checks length first)
    match disc {
        instruction::Deposit::DISCRIMINATOR => __private::__global::deposit(program_id, accounts, rest),
        instruction::Withdraw::DISCRIMINATOR => __private::__global::withdraw(program_id, accounts, rest),
        _ => Err(ErrorCode::InstructionFallbackNotFound.into()),
    }
}

fn deposit(program_id: &Pubkey, accounts: &[AccountInfo], data: &[u8]) -> Result<()> {
    let args = instruction::Deposit::deserialize(&mut &data[..])?;      // stage 3
    let mut bumps = DepositBumps::default();
    let mut remaining: &[AccountInfo] = accounts;
    let mut accs = Deposit::try_accounts(program_id, &mut remaining, data, &mut bumps, &mut BTreeSet::new())?; // stage 4
    let result = my_vault::deposit(
        Context::new(program_id, &mut accs, remaining, bumps), args.amount)?;  // stage 5
    accs.exit(program_id)?;                                              // stage 6
    Ok(result)
}
```

## 3. The program module

The `#[program]` module is the list of instructions. Each `pub fn` inside it becomes one instruction; its first argument is always a `Context<T>` and the rest are the instruction's arguments. Nothing in this module checks accounts; it only receives them already checked. \[Certain\]

### 3.1 The skeleton

```rust
use anchor_lang::prelude::*;

declare_id!("Vau1t11111111111111111111111111111111111111");

#[program]
pub mod my_vault {
    use super::*;

    pub fn initialize(ctx: Context<Initialize>, fee_bps: u16) -> Result<()> {
        require!(fee_bps <= 1_000, VaultError::FeeTooHigh);   // argument check: YOUR job
        let cfg = &mut ctx.accounts.config;
        cfg.admin = ctx.accounts.admin.key();
        cfg.fee_bps = fee_bps;
        cfg.bump = ctx.bumps.config;
        Ok(())
    }

    pub fn deposit(ctx: Context<Deposit>, amount: u64) -> Result<()> {
        instructions::deposit::handler(ctx, amount)   // common style: logic in its own file
    }
}
```

- **`declare_id!`** sets the constant `ID` (and `id()`), the address this program expects to run at. It's used for owner checks (`Account<T>` checks `owner == ID`), PDA derivation and the entry check.
- **`use super::*`** brings the Accounts structs and types from the rest of the crate into the module.
- **Return type** is `Result<()>`, Anchor's `Result<T, anchor_lang::error::Error>`. A handler can also return a value, e.g. `Result<u64>`; Anchor then sets it as **return data** for a calling program to read. \[Certain\]

### 3.2 `Context<T>`: the four fields

In 1.x the type is `Context<'info, T>` (or just `Context<T>`); older versions had `Context<'a, 'b, 'c, 'info, T>`. The fields are the same in all versions: \[Certain\]

| Field | Type | What it is |
| --- | --- | --- |
| `ctx.program_id` | `&Pubkey` | This program's ID |
| `ctx.accounts` | `&mut T` | Your Accounts struct, **already validated** |
| `ctx.remaining_accounts` | `&[AccountInfo]` | Extra accounts passed after the declared ones, **not validated at all** |
| `ctx.bumps` | `TBumps` (generated struct) | Canonical bump for every field with `seeds` + `bump`, e.g. `ctx.bumps.config` |

### 3.3 Instruction arguments

Arguments are Borsh-decoded from the instruction data after the 8-byte discriminator. Any Borsh type works: integers, `Pubkey`, `String`, `Vec<T>`, `Option<T>`, your own `#[derive(AnchorSerialize, AnchorDeserialize)]` structs and enums.

```rust
#[derive(AnchorSerialize, AnchorDeserialize, Clone)]
pub struct OrderParams { pub price: u64, pub size: u64, pub side: Side }

pub fn place_order(ctx: Context<PlaceOrder>, params: OrderParams) -> Result<()> { … }
```

**Arguments are attacker-controlled.** Anchor checks only that they decode. Ranges, zero amounts, `price * size` overflow, enum values that make no sense in context: all yours.

### 3.4 Discriminators

Each instruction is identified by the first 8 bytes of `sha256("global:<fn_name>")`. You can see them in the IDL. In 1.x, override one with `#[instruction(discriminator = <EXPR>)]` on the handler (used to match non-Anchor interfaces like SPL transfer-hook). \[Certain\]

Why you care: renaming a handler changes its discriminator and breaks every client. And two programs with a handler of the same name share a discriminator, which is harmless because programs are called by ID, but matters when one program parses another's instructions via introspection.

### 3.5 `#[access_control]`: run a check before the handler

```rust
#[access_control(only_admin(&ctx))]
pub fn set_fee(ctx: Context<SetFee>, fee_bps: u16) -> Result<()> { … }

fn only_admin(ctx: &Context<SetFee>) -> Result<()> {
    require_keys_eq!(ctx.accounts.admin.key(), ctx.accounts.config.admin, VaultError::Unauthorized);
    Ok(())
}
```

It runs after `try_accounts` and before the handler body. It's equivalent to writing the check at the top of the handler, but easy to miss when reading. When auditing, look for it above every handler.

### 3.6 Organizing a real program

Larger programs keep `lib.rs` thin: each handler calls `instructions::<name>::handler(ctx, …)`, and each `instructions/<name>.rs` holds that instruction's Accounts struct plus its logic. Kamino and Drift both follow variants of this. When auditing, read the Accounts struct and handler of each instruction **together**: they are two halves of one function.

## 4. Accounts structs

An Accounts struct is a typed list of the accounts an instruction expects, **in order**. Each field has a **type** (which runs fixed checks) and optional **constraints** (section 5). The client must pass accounts in exactly the field order; position 0 goes to the first field, and so on. \[Certain\]

```rust
#[derive(Accounts)]
pub struct Deposit<'info> {
    #[account(mut)]
    pub user: Signer<'info>,                       // position 0
    #[account(mut, seeds = [b"vault", user.key().as_ref()], bump = vault.bump)]
    pub vault: Account<'info, Vault>,              // position 1
    pub system_program: Program<'info, System>,    // position 2
}
```

`'info` is the lifetime of the instruction's input buffer (Foundations A.2): every account reference is valid until the instruction ends.

### 4.1 Every account type

| Type | Checks on load | Use for | Watch out |
| --- | --- | --- | --- |
| `Account<'info, T>` | `owner == T::owner()`; 8-byte discriminator; Borsh-decodes `T` | Your own state, or external types with an Anchor wrapper | Proves *a* `T`, not *which* `T`. Needs relationship constraints |
| `AccountLoader<'info, T>` | Owner + discriminator, checked on `load()` / `load_mut()` / `load_init()` | Large zero-copy state (section 6) | `load_init` only checks the discriminator is zero |
| `LazyAccount<'info, T>` | Owner + discriminator; decodes fields only when read | Saving CU/stack on big accounts (feature `lazy-account`) | \[Likely: verify feature name in your version\] |
| `Migration<'info, From, To>` (1.x) | Reads as `From`, writes back as `To` on exit | Upgrading an account's layout | New in 1.x |
| `InterfaceAccount<'info, T>` | Owner ∈ allowed programs (e.g. Token or Token-2022); decodes `T` | Token accounts/mints from either token program | Extensions are not checked |
| `Signer<'info>` | `is_signer` | Users, authorities, payers | Says nothing about owner or data |
| `SystemAccount<'info>` | `owner == System Program` | Plain wallets (e.g. lamport recipients) | Not "a specific wallet" |
| `Program<'info, P>` | `key == P::id()` and executable | Programs you CPI into | 1.x also allows `Program<'info>` (any executable) \[Certain\] |
| `Interface<'info, I>` | Key in a set of program IDs | `TokenInterface` = Token or Token-2022 | Your code must handle both |
| `Sysvar<'info, S>` | `key == S::id()` | Legacy; prefer `S::get()` | — |
| `UncheckedAccount<'info>` | **Nothing** | Anything you validate manually | Must have a `/// CHECK:` doc comment |
| `AccountInfo<'info>` | **Nothing** | Legacy | 1.x emits a deprecation warning in Accounts structs \[Certain\] |

### 4.2 Wrappers

- **`Box<Account<'info, T>>`**: same checks; puts the decoded `T` on the heap. Use when you hit stack-size errors (the SBF stack frame is 4 KB).
- **`Option<Account<'info, T>>`**: the client may pass the **program's own ID** in that position to mean `None`. The handler sees `None` and the type's checks are skipped. Audit every branch that treats `None` as "skip this check". \[Certain\]

### 4.3 `#[instruction(...)]`: using arguments in constraints

```rust
#[derive(Accounts)]
#[instruction(market_id: u64)]
pub struct CreateMarket<'info> {
    #[account(init, payer = admin, space = 8 + Market::INIT_SPACE,
              seeds = [b"market", market_id.to_le_bytes().as_ref()], bump)]
    pub market: Account<'info, Market>,
    #[account(mut)]
    pub admin: Signer<'info>,
    pub system_program: Program<'info, System>,
}

pub fn create_market(ctx: Context<CreateMarket>, market_id: u64) -> Result<()> { … }
```

List the handler's arguments in the same order; you may stop after the last one you need. In 1.x, mismatched types or counts are a compile error; in 0.x, a mismatch could silently decode the wrong bytes. \[Certain\]

### 4.4 Composite (nested) accounts

An Accounts struct can contain another, to reuse common groups:

```rust
#[derive(Accounts)]
pub struct AdminOnly<'info> {
    pub admin: Signer<'info>,
    #[account(has_one = admin)]
    pub config: Account<'info, Config>,
}

#[derive(Accounts)]
pub struct SetFee<'info> {
    pub auth: AdminOnly<'info>,          // positions 0–1
    #[account(mut)]
    pub pool: Account<'info, Pool>,      // position 2
}
// in the handler: ctx.accounts.auth.config.fee
```

The nested struct's checks run in place. **Auditor's note: when a constraint in one struct relies on a field validated in another, read the expanded code to confirm what is actually compared, and in which order.**

### 4.5 `/// CHECK:` comments

```rust
/// CHECK: only used as the PDA signer for the vault; address verified by seeds
#[account(seeds = [b"authority"], bump)]
pub vault_authority: UncheckedAccount<'info>,
```

The compiler forces the comment to exist; it never checks that the comment is true. In audits, read every `/// CHECK:` and try to prove it wrong.

## 5. Constraints in depth

Constraints are the `#[account(...)]` attributes on a field. Each one becomes a few lines of generated code in `try_accounts`. Learn each one as "this exact comparison, and nothing more". The [constraints reference](https://www.anchor-lang.com/docs/references/account-constraints) is the authoritative list for your version. \[Certain\]

### 5.1 Basic flags

| Constraint | Generated check | Not checked |
| --- | --- | --- |
| `mut` | `account.is_writable`, and marks it to be serialized on exit | Who owns it (that's the type) |
| `signer` | `account.is_signer` | Same as using `Signer<'info>` |
| `dup` (1.x) | Allows this `mut` account to also appear in another `mut` slot | Without it, 1.x rejects duplicate mutable accounts; **0.x allows them silently** |

### 5.2 Relationship constraints: where most bugs hide

```rust
#[account(mut, has_one = authority @ VaultError::Unauthorized)]
pub vault: Account<'info, Vault>,
pub authority: Signer<'info>,
```

Generates roughly:

```rust
if vault.authority != authority.key() {
    return Err(VaultError::Unauthorized.into());   // default: ConstraintHasOne
}
```

| Constraint | Generated check | Not checked |
| --- | --- | --- |
| `has_one = x` | `self.x == x.key()` (field and account must share the name) | Anything about `x` itself. If `x` isn't a `Signer` or otherwise validated, you proved nothing |
| `address = expr` | `account.key() == expr` | — Best for fixed accounts: oracles, known programs, admin keys |
| `owner = expr` | `account.owner == expr` | Can't override a typed owner check: `Account<T>` checks `T::owner()` first |
| `executable` | Account is a program | Which program |
| `constraint = expr` | `if !(expr) { Err(ConstraintRaw) }` | Only what the expression says. Read it slowly: `>` vs `>=`, the right field, the right account |

Any of these accepts `@ MyError::X` to return a custom error instead of the generic one.

### 5.3 PDA constraints: `seeds` and `bump`

```rust
#[account(seeds = [b"position", market.key().as_ref(), user.key().as_ref()], bump)]
pub position: Account<'info, Position>,
```

| Form | Generated | Cost / caveat |
| --- | --- | --- |
| `bump` | `find_program_address(seeds, program_id)`; key must match; canonical bump stored in `ctx.bumps.position` | Loops from 255 down: more CU, but always canonical |
| `bump = position.bump` | `create_program_address(seeds + [bump], program_id)`; key must match | Cheap. Safe only if the stored bump was canonical (store `ctx.bumps.x` at init) |
| `seeds::program = other` | Derives with `other` instead of this program's ID | If `other` is user-supplied, the attacker picks the program |

Seed rules that matter:

- Each seed is `&[u8]`: `b"literal"`, `key.as_ref()`, `n.to_le_bytes().as_ref()`. Up to 16 seeds, each ≤ 32 bytes.
- **Seeds define ownership scope.** Include every entity the account belongs to: `[b"position", market, user]` means one position per (market, user). Drop `user` and every user shares one position.
- Seeds referencing a field of the **same** account (`seeds = [b"vault", vault.authority.as_ref()]`) are only meaningful because the type already checked owner and discriminator first.
- 1.x accepts a broader set of Rust expressions in `seeds`, but complex ones may not appear in the IDL for client auto-resolution. \[Certain\]

### 5.4 Lifecycle constraints

**`init`**: create the account.

```rust
#[account(
    init,
    payer = user,
    space = 8 + Position::INIT_SPACE,
    seeds = [b"position", market.key().as_ref(), user.key().as_ref()],
    bump,
)]
pub position: Account<'info, Position>,
#[account(mut)]
pub user: Signer<'info>,
pub system_program: Program<'info, System>,
```

Generated: if the address has 0 lamports, CPI `create_account`; if it was pre-funded, `transfer` the shortfall, then `allocate` and `assign` (so pre-funding can't block init). PDA accounts are signed with the seeds. Then the 8-byte discriminator is written. If the account already has data owned by this program, `init` **fails**: that's the protection against re-initialization. \[Certain\]

**`init_if_needed`**: `init` if the account doesn't exist; otherwise load it as normal and run the other constraints. Requires the `init-if-needed` feature because your handler now runs on both new and existing accounts. Any handler line that sets initial values (`authority = signer`, `balance = 0`) will **reset an existing account**. Prefer a separate `init` instruction unless the account's address already fixes all its fields (e.g. ATAs).

**`zero`**: the account was created by the client (needed above 10 KiB, the CPI allocation limit) and is still zeroed; Anchor checks the discriminator is all zeros, then writes it.

**`realloc = n, realloc::payer = p, realloc::zero = bool`**: resize. Growing takes rent from `p`; shrinking refunds **all** lamports above the new minimum to `p`, including any the account was holding as a vault. `realloc::zero = true` clears newly added bytes (needed if the account shrank earlier in the same transaction). \[Certain\]

**`close = target`**: on exit, move all lamports to `target`, then wipe the account (data zeroed and owner given back to the System Program in current versions). Add `has_one = target` or equivalent so the right person gets the rent back. \[Likely on the exact wipe mechanics per version; read your version's `close` code\]

### 5.5 Evaluation order

1. Fields are processed **top to bottom**.
2. Within a field: the type loads (owner, discriminator, signer…), then `init` runs if present, then the remaining constraints.

Consequence: a `constraint` on field 2 that reads field 3 is reading an account that hasn't been validated yet. Order your struct so that accounts are validated before others depend on them. \[Likely in fine detail; Certain in principle. Confirm with `cargo expand`\]

### 5.6 Reading constraints like an auditor

For each field, write one line: **"This account is proven to be …"**. Example for `position` above: "owned by this program, a `Position`, at the PDA for (this market, this signer)". If you can't finish the sentence with the specific account you need, there's a missing constraint.

## 6. State accounts

State is any struct marked `#[account]`. The macro gives it a discriminator, Borsh serialization, and an `Owner` impl that returns this program's ID, so `Account<'info, T>` can check it. Getting space, layout and lifecycle right is what keeps state safe. \[Certain\]

### 6.1 Defining state

```rust
#[account]
#[derive(InitSpace)]
pub struct Position {
    pub owner: Pubkey,            // 32
    pub market: Pubkey,           // 32
    pub shares: u64,              // 8
    pub last_update_slot: u64,    // 8
    #[max_len(32)]
    pub label: String,            // 4 + 32
    #[max_len(10)]
    pub orders: Vec<u64>,         // 4 + 10 * 8
    pub bump: u8,                 // 1
}
// space = 8 (discriminator) + Position::INIT_SPACE
```

`#[derive(InitSpace)]` computes `INIT_SPACE` from the field types; `#[max_len]` is required for `String` and `Vec` because their size isn't fixed. **The discriminator's 8 bytes are not included**; you always add them yourself. \[Certain\]

### 6.2 Space reference (Borsh)

| Type | Bytes |
| --- | --- |
| `bool`, `u8`, `i8` | 1 |
| `u16`, `i16` | 2 |
| `u32`, `i32` | 4 |
| `u64`, `i64` | 8 |
| `u128`, `i128` | 16 |
| `Pubkey` | 32 |
| `Option<T>` | 1 + size(T) |
| `String` | 4 + max bytes |
| `Vec<T>` | 4 + max\_len × size(T) |
| `[T; N]` | N × size(T) |
| enum | 1 + size of the largest variant |

**Bugs from space:** too small → serialization fails on exit (DoS once a `Vec` fills up). A `Vec` that users can grow without a cap → unbounded loops and CU exhaustion. Never trust `Vec::len()` from data to bound a loop unless writes enforce the cap.

### 6.3 Discriminators

The default account discriminator is `sha256("account:<StructName>")[..8]`. In 1.x you can set your own with `#[account(discriminator = …)]`; an all-zero discriminator is not allowed. **Renaming a struct changes its discriminator**, so existing accounts no longer load. \[Certain\]

### 6.4 Zero-copy for large accounts

Borsh copies the whole account into the stack/heap on every load. For big accounts (order books, large arrays) use zero-copy: the bytes are read **in place**.

```rust
#[account(zero_copy)]
#[repr(C)]
pub struct OrderBook {
    pub market: Pubkey,
    pub count: u64,
    pub orders: [Order; 1024],
}

#[zero_copy]
#[repr(C)]
pub struct Order { pub owner: Pubkey, pub price: u64, pub size: u64 }

#[derive(Accounts)]
pub struct PlaceOrder<'info> {
    #[account(mut, has_one = market)]
    pub book: AccountLoader<'info, OrderBook>,
    pub market: Account<'info, Market>,
    pub user: Signer<'info>,
}

pub fn place_order(ctx: Context<PlaceOrder>, price: u64, size: u64) -> Result<()> {
    let mut book = ctx.accounts.book.load_mut()?;     // owner + discriminator checked here
    let i = book.count as usize;
    require!(i < book.orders.len(), MyError::BookFull);
    book.orders[i] = Order { owner: ctx.accounts.user.key(), price, size };
    book.count += 1;
    Ok(())
}
```

Rules: fields must be plain data (no `String`/`Vec`), the layout is `repr(C)` with alignment padding (Foundations A.9), and the account is usually created client-side then initialized with `zero` because it exceeds the 10 KiB CPI-creation limit. `has_one` works on `AccountLoader` because it loads the data to compare. \[Likely\]

### 6.5 Growing and shrinking: `realloc`

```rust
#[derive(Accounts)]
#[instruction(new_len: u32)]
pub struct Resize<'info> {
    #[account(
        mut,
        has_one = owner,
        realloc = 8 + Profile::space_for(new_len),
        realloc::payer = owner,
        realloc::zero = true,
    )]
    pub profile: Account<'info, Profile>,
    #[account(mut)]
    pub owner: Signer<'info>,
    pub system_program: Program<'info, System>,
}
```

An account can grow by at most 10 KiB per instruction. Check who pays, who gets refunds when shrinking, and that a user can't shrink an account that also stores protocol funds.

### 6.6 Closing

```rust
#[derive(Accounts)]
pub struct ClosePosition<'info> {
    #[account(mut, has_one = owner, close = owner,
              constraint = position.shares == 0 @ MyError::NotEmpty)]
    pub position: Account<'info, Position>,
    #[account(mut)]
    pub owner: Signer<'info>,
}
```

Three checks every close needs: **right signer** (`has_one = owner`), **right recipient** (`close = owner`), and **nothing still owed** (`shares == 0`). A missing third check is a classic: users close a position with debt and the debt disappears.

### 6.7 Changing a layout: versioning and `Migration`

Adding a field to a deployed struct breaks existing accounts (they're too short, or bytes shift). Options:

- Reserve space up front: `pub _reserved: [u8; 64]`.
- Add a `version: u8` field first and branch on it.
- In 1.x, `Migration<'info, Old, New>` loads as `Old` and writes back as `New` on exit (often with `realloc` to the new size). \[Certain\]

## 7. CPIs in Anchor

Anchor wraps `invoke` / `invoke_signed` in a typed `CpiContext`: the program to call, a struct of the accounts it needs, and optionally signer seeds. The privilege rules are exactly those from the deep-dive (part 4); Anchor only makes the call shorter. \[Certain\]

### 7.1 The shape (1.x)

In 1.x, `CpiContext::new` takes the **program ID**; in 0.x it took the program's `AccountInfo` (`ctx.accounts.token_program.to_account_info()`). Per the [1.0 release notes](https://www.anchor-lang.com/docs/updates/release-notes/1-0-0), the redundant program `AccountInfo` field was removed. You'll see both styles in audits. \[Certain\]

```rust
use anchor_lang::system_program::{transfer, Transfer};

pub fn deposit(ctx: Context<Deposit>, amount: u64) -> Result<()> {
    let cpi = CpiContext::new(
        System::id(),                                  // 0.x: ctx.accounts.system_program.to_account_info()
        Transfer {
            from: ctx.accounts.user.to_account_info(),
            to: ctx.accounts.vault.to_account_info(),
        },
    );
    transfer(cpi, amount)
}
```

Even though the ID is now passed directly, the program account still needs to be in the instruction's accounts (keep `system_program: Program<'info, System>` in the struct): the runtime requires the callee to be among the accounts passed. \[Likely\]

### 7.2 Signing as a PDA

```rust
pub fn withdraw(ctx: Context<Withdraw>, amount: u64) -> Result<()> {
    let pool_key = ctx.accounts.pool.key();
    let seeds: &[&[u8]] = &[b"authority", pool_key.as_ref(), &[ctx.bumps.pool_authority]];
    let signer: &[&[&[u8]]] = &[seeds];

    let cpi = CpiContext::new_with_signer(
        Token::id(),
        TransferChecked {
            from: ctx.accounts.vault.to_account_info(),
            mint: ctx.accounts.mint.to_account_info(),
            to: ctx.accounts.user_ata.to_account_info(),
            authority: ctx.accounts.pool_authority.to_account_info(),
        },
        signer,
    );
    token_interface::transfer_checked(cpi, amount, ctx.accounts.mint.decimals)
}
```

- The types read: `&[&[&[u8]]]` is "a list of signers, each a list of seeds, each a byte slice". One PDA signer = one inner list.
- `CpiContext::new(…).with_signer(signer)` is equivalent.
- The runtime derives the PDA from **your** program ID and these seeds. You can only sign for your own PDAs.

### 7.3 After the CPI: `reload()`

```rust
token_interface::transfer_checked(cpi, amount, decimals)?;
ctx.accounts.vault.reload()?;                 // re-read data changed by the Token program
let new_balance = ctx.accounts.vault.amount;
```

`Account<T>` / `InterfaceAccount<T>` are decoded once, in `try_accounts`. Without `reload()` you're reading the pre-CPI copy. In 1.x `reload()` also re-checks the owner. \[Certain\]

The reverse matters too: if your handler changed an `Account<T>` and then CPIs into a program that reads that account, the callee sees the **old bytes**, because Anchor only serializes on exit. Call `ctx.accounts.x.exit(&crate::ID)?` before the CPI if the callee must see your changes. \[Likely\]

### 7.4 Passing extra accounts

```rust
let cpi = CpiContext::new(Token::id(), accounts)
    .with_remaining_accounts(ctx.remaining_accounts.to_vec());
```

Used for transfer hooks, multisig signers, routing. Everything you forward carries its signer/writable privileges into the callee.

### 7.5 Calling another Anchor program: `declare_program!`

Put the other program's IDL at `idls/other_program.json`, then:

```rust
declare_program!(other_program);
use other_program::{cpi, cpi::accounts::Increment, program::OtherProgram};

#[derive(Accounts)]
pub struct CallIt<'info> {
    #[account(mut)]
    /// CHECK: validated by other_program during the CPI
    pub counter: UncheckedAccount<'info>,
    pub other_program: Program<'info, OtherProgram>,
}

pub fn call_it(ctx: Context<CallIt>) -> Result<()> {
    cpi::increment(
        CpiContext::new(other_program::ID, Increment { counter: ctx.accounts.counter.to_account_info() }),
    )
}
```

`declare_program!` generates CPI functions, account types, errors and events from the IDL, with no dependency on the other program's crate. In 1.x some modules were renamed (`utils` → `parsers`, `errors` → `error`). \[Certain\]

### 7.6 Return data

If the callee's handler returns `Result<T>`, the CPI function returns a value whose `.get()` decodes it. Under the hood that's `get_return_data()`; check it came from the program you called.

### 7.7 CPI checklist

- [ ] Program ID pinned (`Program<'info, P>`, `Interface`, or a constant)?
- [ ] Signer seeds scoped to the resource (pool, user), not global?
- [ ] `reload()` after the CPI wherever balances are read again?
- [ ] `exit()` before the CPI if the callee reads state you changed?
- [ ] Forwarded `remaining_accounts` checked, or the callee trusted?

## 8. Errors, events and logs

Errors stop execution and revert the transaction; events and logs only report. Treat errors as security controls and events as untrusted output. \[Certain\]

### 8.1 Custom errors

```rust
#[error_code]
pub enum VaultError {
    #[msg("Amount must be greater than zero")]
    ZeroAmount,          // 6000
    #[msg("Not authorized")]
    Unauthorized,        // 6001
    #[msg("Fee too high")]
    FeeTooHigh,          // 6002
}
```

Custom codes start at **6000** and follow declaration order, so **reordering variants changes the codes** that clients and tests match on. In 1.x a program may have only one `#[error_code]` enum; `#[error_code(offset = N)]` shifts the start. \[Certain\]

### 8.2 The `require!` family

| Macro | Fails when | Notes |
| --- | --- | --- |
| `require!(cond, E)` | `cond` is false | General purpose |
| `require_eq!(a, b, E)` / `require_neq!` | `a != b` / `a == b` | For non-`Pubkey` values; logs both values |
| `require_keys_eq!(a, b, E)` / `require_keys_neq!` | Pubkeys differ / match | Use for `Pubkey` comparisons |
| `require_gt!(a, b, E)` / `require_gte!` | `a <= b` / `a < b` | Read the direction twice in audits |
| `err!(E)` | always (returns `Err`) | `return err!(VaultError::ZeroAmount);` |

```rust
require!(amount > 0, VaultError::ZeroAmount);
require_keys_eq!(ctx.accounts.admin.key(), ctx.accounts.config.admin, VaultError::Unauthorized);
require_gte!(ctx.accounts.vault.amount, amount, VaultError::Insufficient);
```

### 8.3 Built-in error ranges

| Range | Category | Examples you'll see in tests |
| --- | --- | --- |
| 100– | Instruction | `InstructionFallbackNotFound`, `InstructionDidNotDeserialize` |
| 2000– | Constraint violated | `ConstraintMut`, `ConstraintHasOne`, `ConstraintSigner`, `ConstraintRaw`, `ConstraintSeeds` |
| 3000– | Account | `AccountDiscriminatorMismatch`, `AccountOwnedByWrongProgram`, `AccountNotInitialized` |
| 4100 | Program ID | `DeclaredProgramIdMismatch` |
| 6000– | Your `#[error_code]` | — |

&#91;Likely on exact numbers; check `lang/src/error.rs` for your version.\] In logs, an Anchor error looks like:

```text
Program log: AnchorError caused by account: vault. Error Code: ConstraintHasOne.
Error Number: 2001. Error Message: A has one constraint was violated.
```

That line tells you exactly which account and which constraint failed: in PoC tests, assert on it.

### 8.4 Events

```rust
#[event]
pub struct Deposited { pub user: Pubkey, pub amount: u64, pub slot: u64 }

emit!(Deposited { user: ctx.accounts.user.key(), amount, slot: Clock::get()?.slot });
```

`emit!` writes the Borsh-encoded event (with its own 8-byte discriminator) to the program logs. Clients decode it with the IDL.

**`emit_cpi!`** writes the event as a self-CPI instead, so it's stored in the transaction's inner instructions, which can't be truncated like logs. It needs `#[event_cpi]` on the Accounts struct (adds an `event_authority` PDA and the program account) and the `event-cpi` feature. \[Likely on the feature name\]

### 8.5 Security notes

- **Events are not state.** Never let off-chain systems (bridges, indexers, bots) trust an event without checking which program emitted it: any program can log identical bytes. `emit_cpi!` helps because the self-CPI is signed by the program's `event_authority` PDA.
- **`msg!` and `emit!` cost CU**; in loops they can push an instruction over its compute budget.
- **An error is the only thing that undoes state.** "Log and continue" in a handler is a bug pattern: `if bad { msg!("bad"); }` without `return err!` changes nothing.

## 9. Tokens with `anchor_spl`

`anchor_spl` gives you typed wrappers for the token programs: account types (`Mint`, `TokenAccount`), CPI helpers (`transfer_checked`, `mint_to`, `burn`, …) and constraint shortcuts (`token::`, `mint::`, `associated_token::`). Foundations Part E covered the byte layouts; this section is the Anchor API. \[Certain\]

### 9.1 Which module

| Module | Works with | Use when |
| --- | --- | --- |
| `anchor_spl::token` | Legacy Token only (`Account<'info, TokenAccount>`, `Program<'info, Token>`) | Code that must reject Token-2022 |
| `anchor_spl::token_2022` | Token-2022 only | Token-2022-specific instructions |
| `anchor_spl::token_interface` | Either (`InterfaceAccount`, `Interface<'info, TokenInterface>`) | **Default for new code** |
| `anchor_spl::associated_token` | ATA program | Creating/validating ATAs |
| `anchor_spl::token_2022_extensions` | Extension instructions | Configuring extensions |

### 9.2 Constraints recap

```rust
#[account(
    mut,
    token::mint = mint,                  // ta.mint == mint.key()
    token::authority = user,             // ta.owner == user.key()   (the TOKEN owner)
    token::token_program = token_program // account owned by this token program
)]
pub user_ta: InterfaceAccount<'info, TokenAccount>,

#[account(
    mint::authority = mint_authority,    // mint.mint_authority == Some(mint_authority)
    mint::decimals = 6,
    mint::token_program = token_program,
)]
pub mint: InterfaceAccount<'info, Mint>,

#[account(
    associated_token::mint = mint,
    associated_token::authority = user,
    associated_token::token_program = token_program,
)]
pub user_ata: InterfaceAccount<'info, TokenAccount>,   // key == derived ATA address
```

None of these check `delegate`, `close_authority`, frozen state, or extensions. If those matter, check them with `constraint =` or in the handler.

### 9.3 Creating a mint controlled by your program

```rust
#[derive(Accounts)]

    pub admin: Signer<'info>,
    #[account(

        payer = admin,

        mint::token_program = token_program,
    )]

    /// CHECK: PDA that signs as mint authority

    pub pool: Account<'info, Pool>,

```

### 9.4 Token-2022 in Anchor code

- **Always use `transfer_checked`.** Plain `transfer` fails for mints with transfer hooks and some other extensions.
- **Transfer hooks** need extra accounts in the CPI: pass them with `.with_remaining_accounts(...)`; the helper crate `spl-transfer-hook-interface` resolves which ones. \[Likely\]
- **Allowlist extensions.** A protocol that accepts any mint should read the mint's extension list (via `spl_token_2022::extension::StateWithExtensions`) and reject the ones it can't handle: transfer fee, permanent delegate, non-transferable, default-frozen, hooks. \[Certain\]
- **`extensions::*` constraints** (`extensions::transfer_hook::program_id`, `extensions::permanent_delegate::delegate`, …) set extensions on `init` and validate them on existing mints. They only check the extensions they name.

## 10. IDL and TypeScript clients

The IDL is a JSON description of the program, generated by `anchor build`. Clients use it to build instructions; auditors use it as a map of the attack surface. **Nothing in the IDL is enforced on-chain**: an attacker builds transactions by hand and ignores it. \[Certain\]

### 10.1 What's in it (format since 0.30)

```json
{
  "address": "Vau1t11111111111111111111111111111111111111",
  "metadata": { "name": "my_vault", "version": "0.1.0", "spec": "0.1.0" },
  "instructions": [
    {
      "name": "deposit",
      "discriminator": [242, 35, 198, 137, 82, 225, 242, 182],

        { "name": "user", "writable": true, "signer": true },
        { "name": "vault", "writable": true,
          "pda": { "seeds": [
            { "kind": "const", "value": [118, 97, 117, 108, 116] },

      "args": [ { "name": "amount", "type": "u64" } ]
```

### 10.2 Using it from TypeScript

The 1.x package is `@anchor-lang/core` (it was `@coral-xyz/anchor`). \[Certain\]

```ts
import * as anchor from "@anchor-lang/core";
import { Program, BN } from "@anchor-lang/core";
import type { MyVault } from "../target/types/my_vault";

const provider = anchor.AnchorProvider.env();
anchor.setProvider(provider);
const program = anchor.workspace.MyVault as Program<MyVault>;

// call an instruction: args first, then accounts
const sig = await program.methods
  .deposit(new BN(1_000_000_000))
  .accounts({ user: provider.wallet.publicKey })  // vault + system_program resolved from the IDL
  .rpc();

// read state
const [vaultPda] = anchor.web3.PublicKey.findProgramAddressSync(
  [Buffer.from("vault"), provider.wallet.publicKey.toBuffer()], program.programId);
const vault = await program.account.vault.fetch(vaultPda);
console.log(vault.authority.toBase58(), vault.bump);
```

- **Account resolution:** accounts with a fixed `address` or with `pda` seeds the IDL can express are filled in automatically. `.accounts({...})` takes the rest; `.accountsPartial({...})` lets you override resolvable ones too. \[Likely in exact method names for your version\]
- `.rpc()` sends; `.instruction()` returns a `TransactionInstruction` to combine with others; `.simulate()` dry-runs.
- `program.account.<name>.all([filters])` fetches every account of a type (via `getProgramAccounts` with the discriminator filter).

### 10.3 What auditors do with the IDL

1. List every instruction and mark which are permissionless (no admin signer).
2. For each account flagged `writable` but not `signer`, ask who could pass a different one.
3. Compare IDL seeds with the Rust `seeds`: complex seeds the IDL can't express mean clients compute them by hand, a common place for mismatches (but not an on-chain bug).
4. Remember: client-side resolution is a convenience. Never accept "the frontend always passes the right account" as a defence.

## 11. Testing Anchor programs

Anchor generates Rust types for every instruction and Accounts struct, so Rust tests can build instructions without hand-encoding bytes. ### 11.1 Building Anchor instructions in Rust

`#[program]` generates two modules you'll use in every test:

- `my_vault::instruction::Deposit { amount }` → `.data()` gives discriminator + Borsh args.
- `my_vault::accounts::Deposit { user, vault, system_program }` → `.to_account_metas(None)` gives the `AccountMeta` list in field order, with the right `signer`/`writable` flags.

```rust
use anchor_lang::{InstructionData, ToAccountMetas, AccountDeserialize};
use litesvm::LiteSVM;
use solana_sdk::{instruction::Instruction, pubkey::Pubkey,
                 signature::{Keypair, Signer}, transaction::Transaction};

fn deposit_ix(user: Pubkey, vault: Pubkey, amount: u64) -> Instruction {
    Instruction {
        program_id: my_vault::ID,
        accounts: my_vault::accounts::Deposit {
            user,
            vault,
            system_program: anchor_lang::system_program::ID,
        }.to_account_metas(None),
        data: my_vault::instruction::Deposit { amount }.data(),
    }
}

#[test]

    let user = Keypair::new();
    svm.airdrop(&user.pubkey(), 10_000_000_000).unwrap();

    let (vault, _) = Pubkey::find_program_address(&[b"vault", user.pubkey().as_ref()], &my_vault::ID);
    // … send initialize first (same pattern) …

    let tx = Transaction::new_signed_with_payer(
        &[deposit_ix(user.pubkey(), vault, 1_000_000_000)],
        Some(&user.pubkey()), &[&user], svm.latest_blockhash());
    svm.send_transaction(tx).unwrap();

    // read and decode state (checks the discriminator)
    let acc = svm.get_account(&vault).unwrap();
    let v = my_vault::Vault::try_deserialize(&mut acc.data.as_slice()).unwrap();
    assert_eq!(v.authority, user.pubkey());
}
```

### 11.2 Asserting on Anchor errors

When a transaction fails, LiteSVM's error includes the logs. Check for the exact Anchor error:

```rust
let err = svm.send_transaction(tx).unwrap_err();
let logs = err.meta.logs.join("\n");
assert!(logs.contains("Error Code: ConstraintHasOne"), "{logs}");
```

A test that only checks `is_err()` can pass for the wrong reason (a typo in accounts, not the check you care about). Always assert which error fired.

### 11.3 The PoC routine for Anchor findings

1. Write the attack as a test; assert it fails with the expected Anchor error.
2. Remove the constraint you suspect matters; rebuild; the attack must now succeed, and you assert on **state** (balances, account data), not logs.
3. Restore the constraint. In an audit report, the PoC is step 2 against the unmodified target code.

| `anchor test` (Surfpool by default in 1.x, `--validator legacy` for `solana-test-validator`) | Integration tests, TS client tests |
| Trident | Fuzzing Anchor programs with invariants |

## 12. Security: what Anchor guarantees, and what it doesn't

Anchor reliably prevents the *mechanical* bugs (wrong owner, wrong type, missing signer on a typed account, wrong program in a typed CPI). It cannot prevent *semantic* bugs: accounts that are valid but not the right ones, logic, math, and anything in `remaining_accounts`. Almost every real Anchor finding is in the second group. \[Likely\]

### 12.1 Guaranteed vs not

| Anchor guarantees (when you use the right type/constraint) | You must still ensure |
| --- | --- |
| `Account<T>` is owned by the program and has `T`'s discriminator | It's the *specific* `T` this instruction should touch |
| `Signer` signed the transaction | That signer is the authority for *this* resource |
| `Program<P>` is program `P` | The program you CPI into is trustworthy for what you pass it |
| `seeds` + `bump` match | Seeds are scoped tightly enough |
| `init` can't re-initialize | `init_if_needed` handlers don't reset state |
| `close` wipes and refunds | The right recipient; nothing still owed |
| Errors revert everything | Every "bad" branch actually returns an error |
| (1.x) Duplicate `mut` accounts rejected | (0.x) Duplicates handled by hand |

### 12.2 Anchor-specific bug patterns

Each of these is an Anchor-shaped instance of a class in [04, Part 1](./04-advanced-security-and-exploits.md#part-1-bug-classes). This list stays the home for how the *macro* goes wrong; 04 is the home for the vulnerable snippet next to the fix.

**1. Relationship missing.** All types are right, nothing ties them together.

```rust
#[account(mut)] pub pool: Account<'info, Pool>,
#[account(mut)] pub pool_vault: InterfaceAccount<'info, TokenAccount>,   // any vault!
// fix: #[account(mut, address = pool.vault)] or has_one = pool_vault on pool
```

**2. `has_one` against an unchecked account.**

```rust
#[account(has_one = admin)] pub config: Account<'info, Config>,
pub admin: UncheckedAccount<'info>,      // anyone can pass the admin's pubkey without signing
// fix: pub admin: Signer<'info>
```

**3. `init_if_needed` resets state.**

```rust
#[account(init_if_needed, payer = user, space = …, seeds = [b"stake", user.key().as_ref()], bump)]
pub stake: Account<'info, Stake>,
// handler: stake.reward_debt = 0;   ← runs on existing accounts too: free rewards
```

**4. Close without checking what's owed.** `close = user` on a position with open debt: the debt disappears with the account.

**5. Stale data after CPI.** Reading `vault.amount` after a transfer without `reload()`.

**6. Callee reads old state.** Changing `pool.reserve`, then CPIing to a program that reads `pool` before Anchor's `exit()` writes it.

**7. `Option<Account>` as a bypass.**

```rust
pub referrer: Option<Account<'info, Referrer>>,
// handler: if let Some(r) = &ctx.accounts.referrer { require!(r.active, …) }
// attacker passes None to skip a check that should be mandatory
```

**8. Unvalidated `remaining_accounts`.** Deserializing with `Account::try_from` checks owner and type, but not *which* account, whether all required ones are present, or duplicates (deep-dive 6.3).

**9. User-supplied `seeds::program`.** Seeds derived against an attacker-chosen program ID prove nothing.

**10. `realloc` shrink refunds vault lamports** to `realloc::payer`.

**11. Interface handling.** `Interface<TokenInterface>` accepts Token-2022, but the handler assumes `amount` sent = `amount` received (transfer fees), or ignores hooks/permanent delegate.

**12. Lying `/// CHECK:` comments.** "CHECK: verified in handler" — and it isn't.

**13. Constraint ordering.** A `constraint` reading a field of an account validated later in the struct.

**14. Missing `mut`.** Not a security bug by itself, but an instruction that "updates" state silently doesn't; look for accounting that depends on it.

### 12.2a Rust-level pitfalls inside Anchor handlers

Anchor validates accounts; it does nothing for the Rust in your handler. The same panics, truncating casts, rounding mistakes, unbounded loops and borrows held across CPIs (for example a zero-copy `load_mut()` still alive during `transfer_checked`) apply. See [guide 00, §13](./00-rust-fundamentals.md#13-rust-security-for-on-chain-code) for the rules and the security clippy lints that enforce them, and [guide 04, §1.16](./04-advanced-security-and-exploits.md#116-rust-level-bugs-panics-compute-memory-and-the-supply-chain) for vulnerable-vs-fixed examples. Large accounts belong in `Box<Account<…>>` or `AccountLoader` to stay under the 4 KiB SBF stack frame.

### 12.3 Version pitfalls

| If the target uses… | Watch for |
| --- | --- |
| 0.x (any) | Duplicate `mut` accounts allowed: aliasing bugs |
| < 1.0 | Legacy on-chain IDL instructions; zero discriminators could be taken over via IDL instructions (fixed in 1.0) \[Certain per constraints docs\] |
| < 0.30 | Old IDL format, different `close` behaviour, `ctx.bumps` was a map (`ctx.bumps.get("name")`) |
| Any | `overflow-checks` not set in `[profile.release]` |
| Any | Features enabled in `Cargo.toml` (`init-if-needed`) tell you where to look |

### 12.4 Audit checklist for each Anchor instruction

- [ ] Every field: finish the sentence "this account is proven to be …" (5.6)
- [ ] Every authority is a `Signer` and tied to the resource (`has_one`/seeds)
- [ ] Every `UncheckedAccount`: its `/// CHECK:` is true
- [ ] Every `Option<Account>`: `None` doesn't skip a required check
- [ ] Every `init_if_needed`: handler safe on an existing account
- [ ] Every `close`: signer, recipient, nothing owed
- [ ] Every `realloc`: payer, refund, zeroing
- [ ] Every CPI: program pinned, seeds scoped, `reload()` after, `exit()` before if needed
- [ ] `remaining_accounts`: owner, identity, completeness, duplicates
- [ ] Arguments: ranges, zero values, overflow, rounding direction
- [ ] `#[access_control]` and handler-level `require!`s read together with the struct
- [ ] Version: 0.x duplicates, IDL, `overflow-checks`

## Exercises

Eight exercises, easy to hard. **Exercise 1** is a reading drill (no compiler). **Exercises 2–8** build one project, a **staking pool**; each step needs at least one LiteSVM test. Rust language questions belong in [00](./00-rust-fundamentals.md#exercises); the account model and the first Anchor vault are in [01](./01-solana-foundations.md#exercises). This set is about what Anchor generates and what it does not check.

Vulnerable or incomplete snippets are for detection. Do not deploy them. Only test programs you own.

<a id="exercise-1"></a>
### Exercise 1 — Spot the red flag (sections 4–5)

The struct below is deliberately incomplete. For each field, write the "this account is proven to be …" sentence. Then list the missing proofs and the constraint or wrapper that would add them. This is a reading exercise; do not turn it into an attack script.

```rust
// SNIPPET for detection only. Deliberately incomplete. Do not deploy.
#[derive(Accounts)]
pub struct SetFee<'info> {
    #[account(mut)]
    pub config: Account<'info, Config>,
    pub admin: AccountInfo<'info>, // CHECK: must be the admin
    pub new_treasury: SystemAccount<'info>,
}
```

<details>
<summary>Hint</summary>

`Account<Config>` proves owner and type, not *which* config, and not that `admin` signed or matches `config.admin`. `/// CHECK:` is a comment. Ask what happens if `SetFee` also writes `config.treasury = new_treasury.key()`.

</details>

<details>
<summary>Answer</summary>

- `config`: program-owned `Config`, writable. Not proven: it is *the* config (needs `seeds = [b"config"]` or `address = …`).
- `admin`: nothing. Not a `Signer`, not `has_one = admin`, not `address = config.admin`. Anyone can pass the admin's pubkey. Fix: `pub admin: Signer<'info>` plus `has_one = admin` on `config` (or `constraint = admin.key() == config.admin` **and** `Signer`).
- `new_treasury`: a System-owned account. Not proven: it is an intended treasury (could be the attacker's wallet). If the handler assigns it as the new fee destination, that is an admin-equivalent action and must be gated by the same signer check, and usually a timelock or on-chain bound in a real program.
- Also missing: any on-chain bound on the new fee, if the instruction takes `fee_bps` as an argument (Exercise 2).

</details>

<a id="exercise-2"></a>
### Exercise 2 — Setup: Config, admin, fees (sections 1–3)

`anchor init staking`. Add a `Config` with `admin`, `fee_bps`, `bump`; an `initialize_config(fee_bps)` instruction that rejects `fee_bps > 1000`; and `set_fee` gated by `#[access_control]` (or an equivalent constraint plus `Signer`).

**Done when:** a LiteSVM (or `anchor test`) case shows a non-admin cannot call `set_fee`, and you assert on *your* custom error, not a generic transaction failure. A second test shows `fee_bps = 1001` is rejected on init.

<details>
<summary>Hint</summary>

Gate `set_fee` with both a `Signer` and a relationship to `config.admin`. Store a bump if you derive `Config` as a PDA (`[b"config"]`). Assert on the error code you defined in `#[error_code]`.

</details>

<details>
<summary>Solution notes</summary>

- `Config` is `#[account]` with space `8 + 32 + 2 + 1` (discriminator, `Pubkey`, `u16`, bump) unless you add more fields.
- `initialize_config` should `init` the PDA, set `admin = signer`, and `require!(fee_bps <= 1_000, …)`.
- `set_fee` needs `admin: Signer` and `has_one = admin` (Exercise 1 is the warning if you skip either).
- The non-admin test builds the same accounts with a second keypair as signer and expects your error, not `self.unwrap()`.

</details>

<a id="exercise-3"></a>
### Exercise 3 — Accounts and constraints (sections 4–5)

Add a `Pool` per mint, seeds `[b"pool", mint]`, with a vault ATA owned by a `pool_authority` PDA. Write the `Accounts` struct for `stake(amount)` and, for every field, write the "this account is proven to be …" sentence as a comment above it.

**Done when:** the struct compiles, every field has that sentence, and you can point to the constraint that backs each sentence.

<details>
<summary>Hint</summary>

If you cannot write the sentence, the constraint is missing. `token::mint` and `token::authority` are the usual vault proofs. The authority PDA's seeds must include something that scopes it to *this* pool, not to every pool ([01, exercise 3.4](./01-solana-foundations.md#level-3-anchor-and-tokens-parts-d-e) is the same bug in a claim instruction).

</details>

<details>
<summary>Solution notes</summary>

A complete `stake` struct typically proves:

- `user` signed;
- `pool` is this program's `Pool` PDA for `mint`;
- `user_ata` is a token account of that mint whose token-level `owner` is `user`;
- `vault` is a token account of that mint whose authority is `pool_authority`;
- `pool_authority` is the PDA your program will sign for, with seeds that include the pool (or the mint);
- `token_program` is a pinned `Interface<'info, TokenInterface>` (or `Program<'info, Token>` if you only support legacy Token);
- the mint is the one stored on `pool`.

A `/// CHECK:` on `pool_authority` with no `seeds` proves nothing.

</details>

<a id="exercise-4"></a>
### Exercise 4 — State, space, and close (section 6)

Add a `StakePosition` (`[b"position", pool, user]`) with `shares`, `reward_debt`, `bump`. Compute its `space` by hand and check it equals `8 + INIT_SPACE`. Add `close_position` with all three close checks from §6.6.

**Done when:** a unit or print test shows your hand-computed space matches `8 + StakePosition::INIT_SPACE`, and `close_position` will not compile (or will not pass a review checklist) without the right signer, the right recipient, and a "nothing owed" check.

<details>
<summary>Hint</summary>

Space = 8 (discriminator) + every field, with `Pubkey` = 32, `u64` = 8, `u8` bump = 1, and `Option`/`Vec` prefixes as in [00 §10](./00-rust-fundamentals.md#10-serialization-with-borsh). The three close checks: right signer, right recipient, nothing owed.

</details>

<details>
<summary>Solution notes</summary>

If the struct is `pool: Pubkey`, `user: Pubkey`, `shares: u64`, `reward_debt: u64`, `bump: u8`, space is `8 + 32 + 32 + 8 + 8 + 1 = 89`. Watch padding if you later switch to zero-copy (`repr(C)` is a different layout; [01, Part A](./01-solana-foundations.md#part-a-rust-applied-to-solana-types)). `close = user` on a position with `shares != 0` (or unclaimed rewards) is bug pattern 4 in §12.2: add `constraint = position.shares == 0` (and the same for `reward_debt` if it is a debt).

</details>

<a id="exercise-5"></a>
### Exercise 5 — CPIs and tokens (sections 7, 9)

Implement `stake` (user → vault, `transfer_checked`) and `unstake` (vault → user, PDA signs). Measure `received` with `reload()` (or a before/after amount). Support both Token and Token-2022 with `token_interface`.

**Done when:** a test stakes a legacy Token mint and the position's `shares` equal the amount actually received; a second test (or a comment plus a plan) explains what you would measure if the mint had a transfer fee ([01, exercise 4.3](./01-solana-foundations.md#level-4-stretch) / [03 §3.4](./03-solana-security-deep-dive.md#34-token-2022-extensions)).

<details>
<summary>Hint</summary>

Measure `received` after the CPI; `vault.amount` is stale until `reload()`. PDA signer seeds must include the pool. Use `token_interface` so the CPI goes to the program that actually owns the accounts.

</details>

<details>
<summary>Solution notes</summary>

```rust
// Pattern only: measure what arrived, don't credit `amount` blindly.
let before = ctx.accounts.vault.amount;
anchor_spl::token_interface::transfer_checked(/* … */)?;
ctx.accounts.vault.reload()?;
let received = ctx.accounts.vault.amount
    .checked_sub(before)
    .ok_or(ErrorCode::Math)?;
```

`invoke_signed` / `CpiContext::new_with_signer` uses the *calling* program's ID to derive the PDA. If seeds are `[b"authority"]` with no pool or mint, one authority signs for every vault.

</details>

<a id="exercise-6"></a>
### Exercise 6 — Errors and events (section 8)

Emit `Staked` and `Unstaked` events. Make every failure path return a specific custom error, and assert on each in tests.

**Done when:** at least three failure cases (non-admin / wrong fee, insufficient stake, close with shares remaining, or similar) each assert on a distinct error, and a successful `stake` emits `Staked` (logged, or checked via whatever your test stack exposes).

<details>
<summary>Hint</summary>

Add a variant; don't insert in the middle of an existing error enum (self-check 8). Events are not authenticated unless you use `emit_cpi!` — tests that only look at logs must not treat them as a security check.

</details>

<details>
<summary>Solution notes</summary>

Keep error codes stable: append new variants. `require_keys_eq!` / `require!` should name a dedicated error. A test that only checks `result.is_err()` is too weak; match the error. Do not treat an event log as proof that a CPI moved tokens.

</details>

<a id="exercise-7"></a>
### Exercise 7 — Break it, then fix it (section 12)

On a **local branch**, introduce bug patterns 1, 2, 3 and 4 from §12.2, one at a time (relationship missing; `has_one` against an unchecked account; `init_if_needed` resetting state; close with something owed). For each, write a test that the insecure version allows the bad state and the fix rejects it ([01, Part F](./01-solana-foundations.md#part-f-testing-and-your-first-exploit-test)). Then fix and keep the test.

**Done when:** four tests fail against the broken branch and pass against the fixed program. Do not deploy the broken branch. Do not write a steal against anyone else's program.

<details>
<summary>Hint</summary>

One bug at a time so the test names the missing sentence. Pattern 1 is Exercise 1's `SetFee`. Pattern 2: `has_one = admin` while `admin` is `UncheckedAccount`. Pattern 3: `init_if_needed` on `Config` with no "already initialized" path. Pattern 4: you already designed this in Exercise 4.

</details>

<details>
<summary>Solution notes</summary>

For each pattern, the missing sentence and the fix are already in §12.2. The test is the proof: constructed accounts or a second call that the insecure program accepts and the secure one rejects. Leave the tests in the fixed tree as regressions.

</details>

### Exercise 8 — Read someone else's Accounts struct (section 12.4)

Run the §12.4 checklist on Raydium CP-Swap's `swap_base_input.rs` Accounts struct, in the public repo [raydium-io/raydium-cp-swap](https://github.com/raydium-io/raydium-cp-swap). List anything you would question. You are listing questions, not inventing findings. "I cannot see what pins this account" is a valid question. Compare with [03, part 5.1](./03-solana-security-deep-dive.md#51-amm-raydium-cp-swap).

**Done when:** you have a short note, one line per field or per checklist item, written from the code you actually opened (cite the path and revision if you can).

<details>
<summary>Hint</summary>

Work field by field: wrapper, constraints, what is still unproven. Look at vault mints, the authority PDA, Token-2022 / transfer-fee handling, and `remaining_accounts` if present. Do not invent a dollar figure or a "Raydium is broken" claim from this exercise alone.

</details>

<details>
<summary>Solution notes</summary>

There is no single official answer key: the point is the habit. A complete note names the file, walks `swap_base_input`'s accounts, and records questions rather than findings. Anything you still cannot prove belongs in a later [03](./03-solana-security-deep-dive.md#exercises) / [04](./04-advanced-security-and-exploits.md#exercises) pass, not in a made-up report.

</details>

## Answers to the self-checks

**1.** (1) `programs/*/Cargo.toml` (`anchor-lang` version) and `Cargo.lock`. (2) `declare_id!`, the keypair in `target/deploy`, and `Anchor.toml`; `anchor keys sync` rewrites the first and last to match the keypair. (3) The IDL, `target/idl/<name>.json`.

**2.** (1) `has_one` in stage 4; `close` in stage 6; `require!` in stage 5. (2) Only `mut` accounts are serialized back in `exit()`. (3) None.

**3.** (1) `program_id`, `accounts`, `remaining_accounts` (unvalidated), `bumps`. (2) Only that they Borsh-decode. (3) After stage 4, before the handler body.

**4.** (1) `InterfaceAccount<'info, TokenAccount>` with `Interface<'info, TokenInterface>`. (2) It passes the program's own ID in that position. (3) It proves an account owned by this program with `Pool`'s discriminator; not which pool.

**5.** (1) `admin` is never required to sign, so anyone passes the admin's pubkey; make it `Signer`. (2) `bump` calls `find_program_address` (loops, more CU, canonical); `bump = x.bump` calls `create_program_address` once (cheap, trusts the stored bump). (3) The handler runs on existing accounts too, so any initialization logic can reset state. (4) Refunds them to `realloc::payer`.

**6.** (1) 8 + 32 + (1 + 8) + (4 + 5×2) = 63 bytes. (2) To fix field order and padding so the bytes map to the struct the same way every time. (3) Right signer, right recipient, nothing still owed.

**7.** (1) 1.x takes the program ID; 0.x took the program's `AccountInfo`. (2) The runtime derives signer PDAs from the *calling* program's ID. (3) `vault.amount` is the pre-transfer value unless you `reload()`.

**8.** (1) Every existing variant's code shifts by one, breaking clients/tests that match on numbers. (2) `require_keys_eq!`. (3) Any program can log the same bytes; it must check the emitting program (or use `emit_cpi!`'s authenticated self-CPI).

**9.** (1) `anchor_spl::token`. (2) The token account's internal `owner` field equals `user.key()`. (3) So the CPI goes to whichever token program the account actually belongs to.

**10.** (1) Nothing in the IDL fixes that account: look for `has_one`, `address`, `seeds` or a handler check tying it to something. (2) No, it's only for clients. (3) `@anchor-lang/core`.

**11.** (1) The `AccountMeta` list in struct field order with signer/writable flags. (2) The transaction can fail for an unrelated reason. (3) State: balances and account data.
